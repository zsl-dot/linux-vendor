hello：从内核配置到模块运行

本文以 vendor-module/kernel/hello 为例，说明内核、外部模块和 QEMU 的完整关系。

1. 整体链路

linux-source→.config→vmlinux→bzImage→QEMU 自定义内核

模块：hello.c + Kbuild→hello.o + modpost→hello.ko→insmod→hello_init()

2. 配置和编译内核

mkdir -p build/linux-out
make -C linux-source O=build/linux-out x86_64_defconfig
make -C linux-source O=build/linux-out olddefconfig
make -C linux-source O=build/linux-out -j"$(nproc)"

配置写入 build/linux-out/.config。项目脚本额外启用模块、BPF、BTF 和 9P。构建关系为：

内核 .c → .o（obj-y）→ built-in.a → vmlinux → arch/x86/boot/bzImage

bzImage 是 QEMU 用 -kernel 加载的 x86 启动镜像；vmlinux 是供 GDB/KGDB 使用的完整 ELF。

3. 编译 hello.ko

# vendor-module/kernel/hello/Kbuild
obj-m := hello.o

make -C vendor-module/kernel/hello clean
make -C vendor-module/kernel/hello

实际调用：

make -C linux-source O=build/linux-out M=build/vendor-module/hello modules
参数含义
-C使用内核源码中的 Kbuild
O=复用内核配置、头文件和编译参数
M=指定外部模块目录

obj-m 生成可运行时加载的 hello.ko；obj-y 会链接进 vmlinux，不能用 rmmod 卸载。普通 gcc hello.c -o hello 只会生成用户态程序。

4. System.map 与 Module.symvers

文件作用
System.map记录内核符号（如 start_kernel）和链接地址，用于离线地址分析
Module.symvers记录内核导出符号及 CRC，供外部模块 modpost 检查依赖和版本
grep -w start_kernel build/linux-out/System.map
modinfo build/vendor-module/hello/hello.ko | grep -E '^(name|vermagic|license|depends):'

5. 匹配检查

make -C linux-source O=build/linux-out kernelrelease
file build/linux-out/arch/x86/boot/bzImage
test -s build/vendor-module/hello/hello.ko

进入 VM 后执行 uname -r，必须与 kernelrelease 以及模块 vermagic 对应。宿主机版本不同会得到 Invalid module format。

6. 自动验证

cd vendor-module/kernel/hello
./run.sh build

脚本编译模块、复制到 rootfs、修改临时 /init、制作 rootfs.img，再用 QEMU 启动 bzImage。日志在 build/logs/hello-run.log。

7. 手动验证

# 宿主机启动 VM：./lib/vm/virtme-ng/01-run.sh
# 进入 zslmxd@virtme-ng 后：
uname -r; sudo insmod ~/26work/linux-vendor/build/vendor-module/hello/hello.ko; dmesg | grep 'hello:'; sudo rmmod hello; dmesg | grep 'hello:'

看到 hello: module loaded 和 hello: module unloaded 即完成生命周期验证。

8. 改动后重新编译

改动操作
只改 hello.c重新执行模块 make
改内核头文件、配置或导出符号先 ./go.sh kernel，再编译模块
更换架构/编译器/关键配置重新生成配置并全量编译
